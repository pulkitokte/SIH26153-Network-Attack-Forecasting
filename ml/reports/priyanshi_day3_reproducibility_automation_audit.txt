1. AUDIT OBJECTIVE
=======================================================================

The purpose of this audit is to determine whether the current SIH26153
machine-learning workflow is deterministic, validation-safe, reproducible,
and suitable for future automation.

The audit distinguishes between:

1. Internal pipeline reproducibility:
   Whether the existing scripts behave deterministically and protect
   against known data/integrity failures.

2. Fresh-clone reproducibility:
   Whether a new user can clone the repository and reproduce the complete
   ML workflow without relying on undocumented project knowledge.

The audit intentionally does not introduce code changes merely because
a check is absent from an individual script when an upstream or dedicated
validation stage already provides the required protection.

3.1 create_ddos_working_set.py
--------------------------------

Status: PASS WITH DOCUMENTATION GAP

Verified behavior:

- Uses repository-relative paths.
- Reads the CICIDS2017 DDoS source CSV.
- Creates the processed DDoS working dataset.
- Uses contiguous DDoS runs.
- Applies the configured episode-selection logic.
- Produces episode, phase, and sequence-position metadata.
- Does not rely on absolute machine-specific paths.

Current repository limitation:

- The raw CICIDS2017 dataset is not committed to Git.
- The generated working dataset is also not committed.

Interpretation:

The generation logic is reproducible when the required source dataset is
available, but a fresh clone requires documented dataset acquisition and
placement instructions.


3.2 validate_ddos_working_set.py
--------------------------------

Status: INFORMATIONAL VALIDATION

Verified behavior:

- Checks required columns.
- Reports continuity issues.
- Reports missing values and other dataset properties.
- Does not modify the source dataset.
- Does not currently terminate execution through a hard failure for every
  validation finding.

Important distinction:

This validator is report-oriented rather than a complete hard gate.

Therefore it should be treated as an informational audit stage unless
its failure behavior is intentionally strengthened in a future hardening
pass.


3.3 prepare_ddos_features.py
----------------------------

Status: PASS

Verified behavior:

- Required-column failures raise ValueError.
- Infinite values are detected.
- Infinity is converted to NaN.
- Missing feature values are identified.
- Median imputation is applied.
- Constant columns are identified and removed.
- Remaining NaN values are explicitly checked.
- Remaining infinite values are explicitly checked.
- Remaining NaN or Inf values cause ValueError.
- Output CSV is written only after successful preprocessing checks.

Interpretation:

This stage has appropriate hard-failure behavior for the critical
preprocessing integrity conditions.


3.4 create_multihorizon_forecasting_windows.py
-----------------------------------------------

Status: PASS WITH DOCUMENTATION NOTE

Verified behavior:

- Invalid episode-to-split assignment raises ValueError.
- Empty generated windows raise ValueError.
- Observation windows are explicitly checked for DDoS contamination.
- Any DDoS inside an observation window causes ValueError.
- Horizon target distributions are reported.
- Dataset split distributions are reported.
- Windows-per-episode distributions are reported.
- Output is saved after the embedded safety checks.
- A reproducibility report is generated.
- The original prepared dataset is not modified.

Important distinction:

Horizon distributions, split distributions, and episode counts are
reported but are not themselves hard-fail assertions in this section.

Structural integrity is additionally protected by the dedicated
validate_multihorizon_windows.py stage.


3.5 validate_multihorizon_windows.py
------------------------------------

Status: HARD VALIDATION GATE

Verified project behavior:

- Dedicated validation stage exists.
- It is used after forecasting-window generation.
- Critical structural failures terminate validation rather than being
  treated only as informational output.

Interpretation:

This stage provides the primary structural hard gate for generated
forecasting windows.


3.6 build_multihorizon_sequence_tensors.py
-------------------------------------------

Status: PASS - STRONG VALIDATION GATE

Verified behavior:

- Expected feature selection is checked.
- Forecast target and metadata columns are excluded from X.
- Expected feature count is enforced.
- Sequence construction validates expected observation structure.
- Each sequence must have shape:
  (100, 68)
- X NaN count must be zero.
- X Inf count must be zero.
- Train/validation/test X shapes are checked.
- Every horizon y shape is checked.
- X and y sample counts must match.
- Every target must contain only 0/1.
- Full X shape is checked.
- Metadata row count must equal total windows.
- forecast_start_position must equal observation_end_position + 1.
- Observation length must equal 100 flows.
- Stored dataset split must match episode assignment.
- TRAIN episodes must equal 1-15.
- VALIDATION episodes must equal 16-18.
- TEST episodes must equal 19-21.
- Train/validation/test episode overlap is explicitly checked.

Most important safety property:

If any validation check fails, the script raises RuntimeError and
explicitly prevents tensor files from being written.

Therefore:

VALIDATION FAILURE
        |
        v
FAIL
        |
        v
NO TENSOR FILES WRITTEN


3.7 validate_multihorizon_sequence_tensors.py
---------------------------------------------

Status: HARD VALIDATION GATE

Verified project behavior:

- Dedicated tensor validation stage exists.
- It checks tensor integrity after construction.
- Critical failures terminate validation.

Interpretation:

Tensor generation is protected both internally and by a dedicated
validation stage.


3.8 train_multihorizon_gru.py
-----------------------------

Status: PASS WITH HARDENING OBSERVATION

Verified behavior:

- Expected X shapes are checked.
- y sample counts are checked against X.
- TEST metadata row count is checked against X_test.
- TRAIN-only positive-class weights are calculated.
- Zero-positive training horizons cause ValueError.
- Training DataLoader uses deterministic seeded shuffling.
- Validation and test DataLoaders use shuffle=False.
- Best model is selected using validation loss.
- Best validation checkpoint is restored before final evaluation.
- Validation predictions are used for threshold selection.
- Thresholds are selected using validation F1 only.
- TEST data is explicitly excluded from threshold selection.
- TEST is evaluated after validation threshold selection.
- Missing checkpoint causes RuntimeError.
- Model checkpoint stores architecture, thresholds, validation F1,
  positive weights, seed, and training hyperparameters.
- Prediction row count is checked against X_test.
- Test metadata targets are cross-checked against tensor targets.
- Final report records test metrics.
- Final report records that TEST was not used during training or
  threshold selection.

Hardening observation:

The training script itself does not independently check loaded tensors
for NaN/Inf.

This is not a current end-to-end pipeline failure because the upstream
tensor-builder already performs an explicit NaN/Inf hard gate before
creating the training tensors.

Recommendation:

An independent finite-value check may be added to the training script
in a future hardening pass if standalone execution is expected.

5. DATA SPLIT AND LEAKAGE CONTROL
=======================================================================

The authoritative episode split is:

TRAIN:
Episodes 1-15

VALIDATION:
Episodes 16-18

TEST:
Episodes 19-21

The split is episode-based rather than randomly mixing windows from
the same episode across train, validation, and test.

The tensor-builder explicitly checks:

- TRAIN = 1-15
- VALIDATION = 16-18
- TEST = 19-21
- No TRAIN/VALIDATION overlap
- No TRAIN/TEST overlap
- No VALIDATION/TEST overlap

The observation/forecast boundary is also checked:

forecast_start_position =
observation_end_position + 1

Observation length:

100 flows

This is a critical control for the forecasting formulation.

Add a Python dependency manifest containing the required runtime

Allow a fresh environment to install the required Python dependencies

Priority 2 - Dataset setup documentation

Add clear instructions describing:

Priority 3 - End-to-end reproducibility runner

Create a central ML pipeline runner that executes the verified stages
in the correct order and stops immediately when a hard validation stage
fails.

The runner should not duplicate preprocessing/training logic.

It should orchestrate existing scripts rather than replacing them.


Priority 4 - README reproduction section

Document:

- Python version
- environment creation
- dependency installation
- dataset placement
- pipeline execution order
- generated artifacts
- validation gates
- training command
- expected final outputs


Priority 5 - Optional standalone training hardening

Add explicit finite-value validation to train_multihorizon_gru.py so
that direct standalone training also rejects NaN/Inf inputs.

This is optional because the current upstream tensor builder already
provides the required end-to-end protection.


Priority 6 - Optional working-set validation hardening

Evaluate whether validate_ddos_working_set.py should become a true hard
gate for critical structural failures.

Do not change this automatically without deciding which findings are
critical enough to block the pipeline.

17. H500 REPRODUCIBILITY NOTE
=======================================================================

The H500 operating-point behavior was separately investigated.

The H500 test result shows genuine ranking signal but poor operating-point
behavior under the threshold selected from validation F1.

The threshold was selected from VALIDATION only.

Therefore the poor H500 test FAR must not be "fixed" by tuning against
the TEST set.

The current defensible interpretation is:

- H50/H100/H200 are stronger operational forecasting horizons.
- H500 should currently be treated as a longer-range exploratory or
  research forecasting output.
- The limitation should be reported honestly.
- No cosmetic metric manipulation should be performed.
